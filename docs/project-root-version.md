# Project-root CLI selection

A project root (the folder that holds `.bare/` and the collections) can run the
project's CLI release, for example to create a collection with `taba new`,
without a global tool default.

## One source

The harness pin (`.taba-version`, or `.wtc-cli-version` during the rename
window) remains the only version you maintain. For the root, the pin is read
from the harness's **shared owner** (`.bare/<harness>.git`) at the default ref
that the harness registry declares for itself — the commit a new collection starts from.
The root therefore does not depend on which collection you last worked in, an
uncommitted or unpushed pin in a collection, or a development build.

`taba env root` writes the derived selection to `.mise/config.toml` at the
root:

```toml
# Generated by taba from the project harness pin. Do not edit:
# regenerate with `taba env root`. Collections keep their own mise.toml.
[_.taba]
generated = "project-root-selection/v1"
harness = "agent-harness"
ref = "origin/main"
commit = "<commit the pin was read from>"
pin = ".taba-version"

[tools]
"github:lcorneliussen/taba" = "0.2.9"
```

The `[_.taba]` table is provenance that mise ignores. Only the harness owner name
is read back from it. The owner must be a real directory in this project's
`.bare/` whose registry declares that harness. The ref, commit and version are
derived again on every check, so an edited value shows the file as stale rather
than redirecting it.

The file selects the CLI only. It contains no `[env]`, ports, secrets or
collection settings. Inside a collection, that collection's own `mise.toml`
still wins, so collections on different harness revisions keep their own
selection.

## Creating, refreshing and checking

| When | What happens |
| --- | --- |
| `taba env root` in a collection | Creates or refreshes the root file for that collection's harness owner. |
| `taba env root --harness <owner>` at a root without the file | Explicit repair for an existing project. |
| `taba env root --check` | Reports the project source, the root selection (`current`, `stale`, `missing`, `conflict`), this collection's own selection, and root configuration that overrides it. It writes nothing, fetches nothing and runs no hooks. |
| Collection environment generation (`taba new`, `env setup`, catch-up) | Refreshes an existing generated root file from its recorded owner. It never creates a missing file and never touches a file it did not generate. |
| `taba upgrade` | Creates or refreshes the root file. The upgraded pin is local until merged, so the root moves to it after the merge, on the next catch-up. |

A root file that taba did not generate is reported as a conflict and left
unchanged. If your own root `mise.toml` (or `.mise.toml`, `mise.local.toml`,
`.tool-versions`) also selects the CLI, mise prefers yours; `--check` reports it
as an override.

## `taba new` from the root

At a root with a generated selection, `taba new <slug> [repo ...]` accepts the
same arguments and options as in a collection. It validates the recorded
harness owner, fetches it, checks out the new collection's harness at the
project source, and creates the rest of the collection from that checkout. It
reads no other collection. The nearest folder with its own `.bare/` is the project; a generated file in an enclosing folder never stands in for a nearer project without one. If creation fails before anything other than that
harness checkout exists, the checkout and folder are removed. A PR collection
for the harness itself must be created from a collection.

## Without mise

The file is written without mise too; it then only records the project source
for `taba new` at the root. Put the pinned release on `PATH` yourself, as you
would inside collections.
